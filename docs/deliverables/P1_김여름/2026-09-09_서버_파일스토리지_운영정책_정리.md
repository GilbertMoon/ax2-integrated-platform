담당: P1 김여름  
역할: 전체 통합 총괄 / 일정·Git·문서 기준 관리

## 1. 정리 목적

튜터/교수님 추가요청에 따라 4조가 공용 서버의 파일 저장 구조와 Web Client 업로드 권한 기준을 정하고, 1·2·3조가 동일한 기준을 사용하도록 안내하기 위한 운영정책 초안이다.

핵심 방향은 다음과 같다.

- 1·2·3조는 각 기능에서 실제로 발생하는 파일 요구사항을 전달한다.
- 공용 Root Folder, 하위 폴더, 파일명 규칙, Web Client 권한, DB 메타정보, 백업/복구 정책은 4조가 통합 기준으로 결정한다.
- 실제 파일은 File Storage에 저장하고, DB에는 파일 경로/크기/소유자/업로드 시각/관련 FK 등 메타정보를 저장한다.
- 각 조가 운영 서버의 파일 경로나 DB 관리자 권한을 직접 임의 변경하지 않도록 한다.

## 2. 현재 서버 운영 현황

### SSH / 파일 전송
- Ubuntu 서버는 SSH 원격접속이 가능한 상태로 확인됨.
- PowerShell에서 SSH 접속 가능.
- `scp`를 이용한 DB Backup 파일의 서버 전송 방법 확인.
- 운영 보안 방식(SSH Key 등)은 실운영 전 별도 검토.

### DB 이관
현재 필요한 절차는 아래와 같다.

```text
기존 PostgreSQL DB Backup
        ↓
scp로 Ubuntu 서버 전송
        ↓
서버 PostgreSQL Restore
        ↓
Schema / FK / Table / Data 건수 검증
        ↓
Django 연결 및 Regression
```

공식 DB Host/Port/DB 기준은 팀 공통값으로 하나로 확정해야 한다.

## 3. File Storage 기본정책

### 3.1 기본 원칙

```text
Web Client
    ↓
Django Upload 처리
    ↓
공용 File Storage
    ↓
DB에는 File Metadata 기록
```

DB에 기록할 주요 정보 예시는 다음과 같다.

```text
file_id
owner_user_id
related_object_id
original_name
stored_name
relative_path
file_size
mime_type
uploaded_at
```

### 3.2 4조가 결정할 항목

- 공용 File Storage Root
- 기능별 하위 폴더 구조
- 파일명 규칙
- Web Client 업로드 권한
- 다운로드 권한
- 허용 확장자/최대 크기
- DB File Metadata 구조
- 덮어쓰기/버전관리 기준
- 보관기간/삭제정책
- Backup/Restore 기준
- Windows/Linux 경로 차이 처리

### 3.3 각 조에 요구할 항목

1·2·3조는 아래 요구사항만 회신한다.

- 어떤 파일이 실제로 발생하는지
- 누가 업로드/다운로드하는지
- 파일 최대 크기
- 예상 개수/누적량
- 파일과 연결되는 DB Key
- 재업로드 방식
- 보관기간
- 접근권한
- 서버 이관 시 보존 여부

저장 Root나 Linux 폴더 구조 자체는 각 조가 정하지 않고 4조 공통기준을 따른다.

## 4. 얼굴사진 저장정책 방향

얼굴사진은 용도가 다르므로 저장방식을 분리한다.

### 프로필 사진
- 현재 DB 저장 방식 유지 가능
- 사용자당 소수 파일이므로 현 단계에서는 기존 구현 유지 가능
- 향후 공용 File Storage로 통합할지 별도 검토

### 일별 출석 사진
- 누적량이 많으므로 File Storage 저장 방향
- DB에는 파일 자체가 아니라 경로와 메타정보 저장

예시:

```text
/srv/ax2/data/attendance/
└── users/
    └── user_28/
        ├── checkin_20260909_091532.jpg
        ├── checkin_20260910_090104.jpg
        └── checkin_20260911_085958.jpg
```

운영 화면에서는 사용자 이름을 표시하더라도 서버 폴더는 변하지 않는 `user_id` 기준으로 관리한다.

DB 예시:

```text
user_id = 28
attendance_id = ...
file_path = attendance/users/user_28/checkin_20260909_091532.jpg
captured_at = 2026-09-09 09:15:32
file_size = ...
```

## 5. 조별 파일 사용 현황

### 2조 PRD
현재 확인 결과:

- PRD는 DB 기반 Page/Document Data
- 사용자 파일 업로드 기능 없음
- MD Export 시 서버에 파일을 저장하지 않음
- 현재 PRD 자체는 공용 File Storage 직접 사용 대상이 아님
- 향후 이미지/첨부파일 기능 추가 시 4조 공통 정책 적용

추가 확인:
- 이미지 첨부 존재 여부
- Export 과정 임시파일 생성 여부
- 향후 첨부기능 계획 여부

### 3조 LMS
3조 조장 재확인 결과, 현재 실제 서버 저장 대상은 다음과 같다.

- 과제 제출물
- 과제 첨부파일

초기에는 학생 GitHub Repository URL을 제출받아 평가하는 방식 때문에 파일스토리지 필요성이 크지 않다고 판단했으나, 실제 LMS 내부에는 과제 관련 파일이 서버에 저장되고 있음이 확인되었다.

현재 3조에서 미정인 운영정책:

- 삭제 기준
- 보관기간
- 업로드/다운로드 권한
- 파일명 규칙
- 저장 폴더 규칙
- 재제출 시 덮어쓰기/버전관리
- Backup/Restore
- 서버 이관 시 파일 보존 방식

추가 확인할 요구사항:

- 파일 최대 크기
- 허용 확장자
- 학생/튜터/관리자별 권한
- 제출 완료 후 삭제 가능 여부
- 프로젝트 종료 후 보관기간

## 6. 3조 LMS GitHub URL 평가 방식의 운영 Pain Point

현재 학생이 GitHub Repository URL을 제출하고 평가자가 링크를 직접 열어 확인하는 방식은 File Storage 사용량은 줄일 수 있으나, 평가 운영 측면에서 다음 문제가 있다.

- 학생 수 × 과제 수만큼 평가자가 링크를 반복해서 열어야 함
- 단순 Repository URL만 저장하면 제출 시점의 상태가 고정되지 않음
- 제출 후 학생이 코드를 수정하면 평가 당시 상태와 현재 상태가 달라질 수 있음
- 어느 Branch/Commit을 평가했는지 추적하기 어려움
- 1차 제출/재제출/최종 제출 이력 관리가 약함
- 여러 평가자가 서로 다른 시점의 코드를 볼 수 있음
- Repository 삭제/Private 전환 시 과거 제출 결과 재확인이 어려움
- 평가 완료/미완료 상태가 사람의 기억이나 별도 기록에 의존할 수 있음
- 점수와 평가 근거의 Audit Trail이 약함

소스 전체를 서버에 저장하지 않더라도 LMS DB에는 최소한 아래 정보를 저장하는 구조가 필요하다.

```text
student_id
assignment_id
repository_url
branch
commit_sha
submitted_at
evaluated_at
evaluator_id
score
feedback
submission_status
```

필요 시 향후 제출 시점의 Snapshot ZIP/Git archive를 File Storage에 보관하는 방식도 검토할 수 있다.

## 7. Web Client 권한과 DB 권한 분리

교수님 요청사항은 4조가 Web Client 업로드 권한 및 공용 저장기준을 만들어 1·2·3조에 전달하는 방향으로 이해한다.

다음 권한은 서로 구분한다.

### 각 조에 제공 가능한 권한
- 웹에서 정해진 Upload 기능 사용
- 정해진 API/공통 업로드 모듈 사용
- 자기 기능 범위의 파일 조회/다운로드

### 제공하지 않아야 하는 권한
- PostgreSQL SuperUser 권한
- 운영 서버 Root 권한
- `/srv/ax2/data` 전체 임의 삭제 권한
- 다른 조 파일에 대한 무제한 수정 권한

즉 `Web Client Upload 권한 != Server 관리자 권한 != DB 관리자 권한`으로 분리한다.
