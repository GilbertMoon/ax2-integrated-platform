# 2026-09-01 통합 공통 모델 사전 분석

## 1. 목적

2조 LMS 코드가 아직 전달되지 않은 상태에서, 향후 코드 인수 및 통합 작업 시 충돌 여부를 빠르게 판단할 수 있도록 4조 Core의 공통 모델과 주요 FK 연결 구조를 사전 확인한다.

> 현재 단계에서는 코드 수정이나 Migration을 수행하지 않고 구조 분석만 진행한다.

## 2. 확인 범위

- `accounts.User`
- `rounds.EvaluationRound`
- `rounds.RoundParticipant`
- `teams.Team`
- `teams.TeamMembership`
- 주요 앱의 User / Team / EvaluationRound / RoundParticipant 참조 관계
- `config/urls.py`의 주요 기능 URL 연결 구조

## 3. 핵심 구조

```text
accounts.User
    ↓
rounds.RoundParticipant
    ↓
teams.TeamMembership
    ↓
teams.Team
    ↓
rounds.EvaluationRound
```

### User

- `accounts.User`가 통합 플랫폼의 사용자 기준 모델이다.
- `username` 대신 `email`을 로그인 식별자로 사용한다.
- 역할(`role`)과 승인 상태(`approval_status`)를 User에서 관리한다.
- 다른 기능에서 사용자 연결이 필요한 경우 `settings.AUTH_USER_MODEL` 기준으로 연결되는 구조를 확인했다.

### EvaluationRound

- 평가 회차의 기준 모델이다.
- `EvaluationRound`은 Team과 RoundParticipant가 연결되는 상위 기준이 된다.
- 평가 템플릿 및 평가 가중치 등의 회차별 설정도 관리한다.

### RoundParticipant

- 특정 `EvaluationRound`에 참여한 사용자를 나타낸다.
- `round + user` 조합이 유일하도록 제약되어 있다.
- 사용자 정보와 별도로 학생번호/이름 snapshot을 보관한다.

### Team / TeamMembership

- `Team`은 `EvaluationRound`에 소속된다.
- `TeamMembership`을 통해 `RoundParticipant`와 Team이 연결된다.
- `RoundParticipant`는 `TeamMembership`에서 OneToOne 관계로 사용되고 있어 한 회차 참가자의 팀 소속 관계를 명확하게 관리한다.

## 4. 주요 FK 참조 확인 결과

| 위치 | 연결 대상 | 통합 관점 |
|---|---|---|
| `accounts.models.ScheduledEmail` | `teams.Team` | 특정 팀 대상 메일 발송에 사용 |
| `rounds.models.RoundParticipant` | `accounts.User` | 회차 참가자와 공통 사용자 연결 |
| `teams.models.TeamMembership` | `teams.Team` | 팀 소속 연결 |
| `teams.models.TeamMembership` | `rounds.RoundParticipant` | 회차 참가자와 팀 연결 |
| `results.models` | `Team` | 평가 결과와 팀 연결 |
| `reviews.models` | `Team` | 팀 평가 대상 연결 |
| `rounds.models.EvaluationRound` | `QuestionTemplate` | 회차와 평가 문항 연결 |

## 5. URL 구조 확인

현재 주요 기능은 다음과 같이 분리되어 있다.

- `/accounts/` : 계정 기능
- `/teams/` : 팀 기능
- `/student/team/` : 학생 팀 화면
- `/reviews/` : 평가/리뷰 기능
- `/results/` : 결과 기능
- `/manage/` : 회차 관리 기능
- `/notifications/` : 알림 기능

Google/Kakao 로그인 URL도 `accounts`에 존재하지만, 이는 기존 인증 기능으로 확인했으며 이번 통합 사전 분석 범위에서는 별도 작업 대상으로 포함하지 않았다.

## 6. 2조 코드 인수 후 확인 기준

2조 LMS 코드가 전달되면 아래 항목을 우선 비교한다.

1. 사용자 모델이 `accounts.User`를 직접 참조하는지
2. 별도의 User/Student 모델을 가지고 있는지
3. Team 또는 팀원 모델을 별도로 가지고 있는지
4. 회차/참가자 개념이 `EvaluationRound` / `RoundParticipant`와 어떻게 대응되는지
5. 과제/제출 기능이 기존 Core 모델과 중복되는지
6. 기존 Core의 User / Team / Round에 FK로 연결 가능한지
7. 별도 Migration이 필요한지
8. 기존 Core 모델을 수정해야 하는지

## 7. 현재 판단

- 4조 Core의 공통 기준은 `User → RoundParticipant → TeamMembership → Team → EvaluationRound` 관계를 중심으로 확인할 수 있다.
- 2조 LMS의 실제 코드를 받기 전에는 구체적인 FK 변경이나 Migration 범위를 확정하지 않는다.
- 2조 코드 인수 후 모델 구조를 위 기준과 대조하여 `통합 / 유지 / 분리 / 수정 필요`로 구분한다.
- 현재 단계에서는 코드 수정 없이 통합 대비 구조 파악을 완료한다.
