# 2026-09-15 Repository 운영 구조 검토

## 1. 작업 배경

3조 프로젝트를 통합 프로젝트에 반영한 이후 통합 서버에서 실제 실행되는지 확인하고, 주요 기능 및 화면 연결 상태와 사이드바 수정까지 검증했다.

통합 자체의 동작 여부를 확인한 뒤, 이후 실제 배포 및 운영 과정까지 고려하여 현재의 조별 Repository 기반 개발·통합 방식이 최종 운영 단계에서도 적절한지 검토했다.

## 2. 오늘 확인한 내용

### 2.1 3조 통합 서버 검증
- 3조 프로젝트를 통합 프로젝트에 반영한 상태 확인
- 통합 서버에서 3조 기능이 실행되는지 확인
- 주요 기능 및 화면 연결 상태 확인
- 통합 과정에서 발견된 오류 상태 확인

### 2.2 사이드바 수정
- 통합 프로젝트 기준으로 사이드바 메뉴 구성 수정
- 수정된 메뉴와 실제 화면 연결 상태 확인

## 3. 통합 과정에서 발견한 구조적 문제

3조 프로젝트를 실제 통합 서버에서 실행하고 이후 배포·운영 과정까지 고려하면서, 단순히 각 조의 Repository에서 개발한 결과물을 통합 시점에 하나의 프로젝트로 병합하는 현재 방식에는 운영 측면의 문제가 있을 수 있음을 확인했다.

최종적으로 하나의 서비스로 배포·운영되는 상황에서 각 조의 개발 소스가 여러 Repository로 계속 분리되어 있다면, 이후 기능 수정 및 추가가 발생할 때 통합 작업이 반복될 가능성이 있다.

또한 실제 배포 대상인 통합 프로젝트와 각 조가 계속 개발하는 Repository가 분리되어 있으면 최신 코드 기준, 변경사항 관리, 재통합 및 재배포 과정에서 관리 기준이 복잡해질 수 있다.

## 4. 현재 검토 방향

현재 단계에서는 기존 조별 Repository를 바로 삭제하거나 통합 Repository로 즉시 전환하는 것으로 결론을 확정하지 않는다.

다음 두 가지 방식을 비교하여 팀 논의를 통해 최종 방향을 결정할 필요가 있다.

### 방식 A. 통합 Repository 중심 운영
- 하나의 통합 Repository를 최종 개발·관리 기준으로 사용
- 기능 개발 및 수정도 통합 Repository를 기준으로 진행
- 최종 배포 대상과 개발 소스의 기준을 일치시킴

### 방식 B. 기존 조별 Repository 유지 + 필요 시 통합
- 각 조가 기존 Repository에서 계속 개발
- 변경사항 발생 시 통합 프로젝트에 반영
- 배포 전 통합 및 검증을 반복

## 5. 현재 판단

**Repository 운영 방식에 대한 최종 결론은 아직 확정하지 않은 상태이다.**

3조 통합을 실제 수행하면서 통합 서버 실행 및 화면 연결까지 확인한 경험을 바탕으로, 개발 단계뿐 아니라 배포 이후 운영까지 고려했을 때 Repository 구조를 별도로 검토해야 한다는 문제를 도출했다.

특히 최종 서비스가 하나의 통합 서비스라면 하나의 통합 Repository를 기준으로 개발·운영하는 방식이 적절할 가능성이 있으나, 기존 조별 Repository의 작업 이력과 개발 흐름을 어떻게 유지하거나 전환할지까지 함께 검토한 후 결론을 내릴 예정이다.
