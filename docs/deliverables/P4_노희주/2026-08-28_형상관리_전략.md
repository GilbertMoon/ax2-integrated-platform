# AX2 통합 플랫폼 형상관리 전략

## 1. 문서 개요

| 항목 | 내용 |
|---|---|
| 문서명 | AX2 통합 플랫폼 형상관리 전략 |
| 작성일 | 2026-08-28 |
| 작성자 | P4 노희주 |
| 적용 대상 | AX2 통합 플랫폼 전체 개발팀 |
| 기준 저장소 | `GilbertMoon/ax2-integrated-platform` |
| 핵심 원칙 | 하나의 코드베이스에서 협업하되 공유 Core 테이블의 변경 권한은 4조가 관리한다. |

## 2. 목적

본 전략은 1·2·3·4조가 하나의 Django 프로젝트를 공동 개발하는 과정에서 코드 충돌과 데이터베이스 스키마 불일치를 줄이고, 공유 데이터의 안정성을 확보하기 위한 형상관리 기준을 정의한다.

통합 시스템은 각 조의 기능이 `accounts_user`, `teams_team`, `rounds_evaluationround` 등 동일한 Core 데이터를 참조한다. 따라서 저장소를 조별로 분리하지 않고 모노레포로 운영하며, 공유 영역과 조별 영역의 소유권을 명확히 구분한다.

## 3. 핵심 운영 원칙

> 각 조는 담당 앱 안에서 자율적으로 개발한다. 단, 모든 조가 함께 사용하는 `accounts`, `teams`, `rounds` 영역은 4조의 검토와 승인 없이 변경할 수 없다.

- 전체 팀은 하나의 저장소와 하나의 통합 코드베이스를 사용한다.
- 1·2·3조는 각 조가 담당하는 앱을 중심으로 개발한다.
- 공유 모델과 Core 설정은 4조가 소유하고 변경을 통제한다.
- 모든 변경은 작업 브랜치와 Pull Request를 통해 반영한다.
- DB 스키마가 변경되면 Migration과 통합 ERD를 같은 Pull Request에서 함께 갱신한다.
- 서브팀의 점수 전송부터 최종 계산까지의 흐름은 필수 회귀 테스트 대상으로 유지한다.

## 4. 저장소 구조와 소유권

통합 ERD와 외래키 관계를 일관되게 관리하기 위해 하나의 저장소를 사용하는 모노레포 방식을 적용한다.

```text
ax2-integrated-platform/
├── config/             # Django 설정 및 URL                     → 4조
├── accounts/           # 공유 사용자 모델(accounts_user)        → 4조 단독 관리
├── teams/              # 공유 팀 모델(teams_team)                → 4조 단독 관리
├── rounds/             # 공유 평가 라운드 및 참여자               → 4조 단독 관리
├── reviews/            # 동료·튜터 평가                           → 4조
├── results/            # 점수 계산 및 결과                        → 4조
├── notifications/      # 알림                                    → 4조
├── audit/              # 감사 로그                               → 4조
├── notices/            # 공지                                    → 4조
├── peer_reviews/       # 평가 확장 앱 골격                        → 4조
├── team_reviews/       # 팀 평가 확장 앱 골격                     → 4조
├── garden/             # 1조 기능(통합 시 추가)                   → 1조
├── lms/                # 2조 기능(통합 시 추가)                   → 2조
├── prd/                # 3조 기능(통합 시 추가)                   → 3조
├── attendance/         # 4조 신규 근태 기능(개발 시 추가)          → 4조
├── face_recognition/   # 4조 신규 얼굴인식(개발 시 추가)           → 4조
├── templates/          # 공통 및 앱별 HTML                        → 하위 경로별 소유
├── static/             # 공통 및 앱별 CSS·JS                     → 하위 경로별 소유
├── deploy/             # 서버 배포 설정                           → 4조
├── docs/               # 설계·ERD·운영 문서                       → 분야별 담당
└── .github/workflows/  # CI/CD                                   → 4조
```

`garden`, `lms`, `prd`, `attendance`, `face_recognition`은 확인한 기존 4조 메인에는 아직 존재하지 않으며, 통합 또는 신규 개발 시 추가할 목표 앱이다. 반면 `peer_reviews`와 `team_reviews`는 현재 앱 골격만 있으므로 실제 사용 여부와 기존 `reviews`와의 역할 중복을 통합 전에 확정한다.

### 4.1 소유권 적용 기준

| 변경 영역 | 주 작업 주체 | 필수 리뷰 주체 |
|---|---|---|
| `garden/` | 1조 | 1조 담당자 또는 4조 연동 창구 |
| `lms/` | 2조 | 2조 담당자 또는 4조 연동 창구 |
| `prd/` | 3조 | 3조 담당자 또는 4조 연동 창구 |
| `accounts/` | 4조 | 4조 Core 모델 담당자 |
| `teams/` | 4조 | 4조 Core 모델 담당자 |
| `rounds/` | 4조 | 4조 Core 모델 담당자 |
| `reviews/`, `results/` | 4조 | 4조 평가·집계 담당자 |
| `notifications/`, `audit/`, `notices/` | 4조 | 4조 Core 담당자 |
| `config/`, `deploy/`, `.github/workflows/` | 4조 | 4조 형상관리 또는 CI/CD 담당자 |
| `templates/`, `static/` | 해당 기능 담당 조 | 연결된 앱의 CODEOWNER |

## 5. 브랜치 전략

### 5.1 브랜치 역할

| 브랜치 | 역할 | 직접 Push |
|---|---|---|
| `main` | 배포 가능한 안정 버전 | 금지 |
| `develop` | 각 조의 기능을 모아 통합 검증하는 브랜치 | 금지 |
| `team1/기능명` | 1조 기능 개발 | 허용 |
| `team2/기능명` | 2조 기능 개발 | 허용 |
| `team3/기능명` | 3조 기능 개발 | 허용 |
| `team4/기능명` | 4조 및 Core 기능 개발 | 허용 |

브랜치 이름은 작업 목적을 알아볼 수 있도록 작성한다.

```text
team1/garden-ranking
team2/assignment-submission
team3/prd-ai-coach
team4/score-calculation
```

### 5.2 병합 흐름

```text
팀별 작업 브랜치
        ↓ Pull Request + 담당자 리뷰
develop
        ↓ 전체 통합 및 회귀 테스트
main
        ↓
배포
```

### 5.3 Pull Request 승인 규칙

- `develop`과 `main`에는 직접 Push하지 않는다.
- 모든 병합은 Pull Request를 통해 수행한다.
- 자기 팀 앱 디렉토리만 수정한 Pull Request는 팀 내 리뷰 1인의 승인 후 병합할 수 있다.
- `accounts`, `teams`, `rounds` 중 하나라도 변경한 Pull Request는 반드시 4조의 승인을 받아야 한다.
- CI 테스트가 실패한 Pull Request는 병합하지 않는다.
- 리뷰 승인 후 코드가 추가로 변경되면 다시 승인을 받는다.

### 5.4 릴리스 태그

로드맵의 Phase가 종료될 때마다 검증된 `main` 커밋에 버전 태그를 생성한다.

```text
v0.1  Phase 1 완료
v0.2  Phase 2 완료
v0.3  Phase 3 완료
```

태그 메시지에는 완료된 범위, 주요 변경 사항, 알려진 제한 사항을 기록한다.

## 6. Migration 및 DB 소유권 규칙

### 6.1 공유 테이블

다음 공유 테이블과 해당 Django 앱의 Migration은 4조만 생성·수정한다.

- `accounts_user`
- `teams_team`
- `rounds_evaluationround`
- `accounts/migrations/`
- `teams/migrations/`
- `rounds/migrations/`

또한 공유 데이터를 계산하고 노출하는 `reviews`, `results`는 4조 Core 보호 영역으로 관리한다. 이 두 앱의 모델 또는 계산 규칙 변경은 공유 테이블 변경과 동일하게 4조 리뷰를 필수로 한다.

1·2·3조가 공유 테이블에 필드 또는 제약조건 추가가 필요할 경우 코드를 직접 변경하지 않고 Issue 또는 Core 스키마 변경 요청서를 제출한다.

### 6.2 공유 스키마 변경 절차

1. 요청 조가 변경 목적, 필요한 필드, 사용 화면과 영향 범위를 작성한다.
2. 4조 Core 모델 담당자가 기존 모델·API·Migration 영향을 검토한다.
3. 승인된 변경은 4조가 모델과 Migration에 반영한다.
4. 통합 ERD의 Mermaid 원본도 동일한 Pull Request에서 변경한다.
5. Migration 및 전체 회귀 테스트 통과 후 `develop`에 병합한다.

### 6.3 조별 앱 Migration

- 각 조는 `garden`, `lms`, `prd` 등 자기 앱의 Migration을 자율적으로 관리한다.
- 공유 모델을 참조하는 외래키를 추가하거나 변경할 때는 4조 연동 창구에 사전 공지한다.
- 외래키 대상 필드명 또는 삭제 정책을 임의로 변경하지 않는다.
- Migration 파일을 삭제하거나 번호를 임의로 재작성하지 않는다.
- 스키마 변경 시 Migration과 ERD 변경을 하나의 Pull Request로 제출한다.

## 7. CODEOWNERS 운영

GitHub의 `.github/CODEOWNERS`를 이용해 변경 경로에 따라 리뷰어가 자동 지정되도록 한다.

```text
/garden/                         @1조_담당자
/templates/garden/               @1조_담당자
/static/garden/                  @1조_담당자
/lms/                            @2조_담당자
/templates/lms/                  @2조_담당자
/static/lms/                     @2조_담당자
/prd/                            @3조_담당자
/templates/prd/                  @3조_담당자
/static/prd/                     @3조_담당자
/accounts/ /teams/ /rounds/      @4조_전체
/reviews/ /results/              @4조_전체
/templates/accounts/             @4조_전체
/templates/teams/                @4조_전체
/templates/rounds/               @4조_전체
/templates/reviews/              @4조_전체
/templates/results/              @4조_전체
/config/                         @4조_전체
/deploy/                         @4조_전체
/.github/                        @4조_형상관리담당자
```

실제 적용 시에는 위 표기 대신 각 담당자의 정확한 GitHub 사용자명 또는 GitHub Team을 입력한다. CODEOWNERS만으로 승인이 강제되지는 않으므로 `main`과 `develop`의 Branch Protection Rules에서 다음 항목을 활성화한다.

- Pull Request 필수
- CODEOWNER 승인 필수
- 필수 CI 상태 검사 통과
- 승인 이후 변경 발생 시 기존 승인 무효화
- 관리자 포함 직접 Push 제한

## 8. CI/CD 전략

### 8.1 Pull Request 검사

Pull Request에서는 변경된 디렉토리를 기준으로 관련 앱 테스트를 우선 실행한다.

| 변경 경로 | 기본 테스트 범위 |
|---|---|
| `garden/` | 1조 앱 테스트 |
| `lms/` | 2조 앱 테스트 |
| `prd/` | 3조 앱 테스트 |
| `accounts/`, `teams/`, `rounds/` | Core 및 연동 앱 테스트 |
| `reviews/`, `results/` | 평가 입력·계산·결과 회귀 테스트 |
| `templates/`, `static/` | 연결된 앱 테스트 및 화면 Smoke Test |
| `deploy/`, `.github/workflows/` | 배포 설정 및 CI 구성 검증 |
| `config/`, 공통 설정 | 전체 테스트 |

### 8.2 통합 브랜치 검사

`develop` 또는 `main`에 병합할 때는 전체 통합 테스트를 실행한다. 확인한 기존 4조 메인에는 `CalculationRun`과 `EvaluationResult`는 있지만 `ScoreInput` 모델은 아직 없다. 따라서 다음 흐름은 현재 구현 설명이 아니라, 서브팀 통합 과정에서 4조가 설계·추가할 목표 회귀 테스트 시나리오로 관리한다.

```text
서브팀 점수 Push
    ↓
ScoreInput 저장(추가 예정)
    ↓
calculationrun 실행
    ↓
최종 결과 생성 및 조회
```

`ScoreInput`의 실제 모델명, 입력 단위, 중복 방지 키, 재전송 정책과 API 계약은 구현 전에 4조가 확정한다. 기존 Core의 `CalculationRun` 및 `EvaluationResult`와 연결하되, 1·2·3조가 `results` 테이블에 직접 쓰지 않고 승인된 입력 인터페이스를 사용하도록 한다.

### 8.3 Core 변경 영향에 따른 회귀 테스트

실제 외래키 연결을 기준으로 Core 변경 시 최소 테스트 범위를 다음과 같이 적용한다.

| 변경 영역 | 함께 확인할 영역 |
|---|---|
| `accounts` | `rounds`, `teams`, `reviews`, `results` 및 로그인·권한 |
| `rounds` | `teams`, `reviews`, `results` 및 라운드 참여자 |
| `teams` | `reviews`, `results` 및 팀원 구성 |
| `reviews` | 평가 제출, 잠금, 튜터 평가, 결과 계산 입력 |
| `results` | 계산 실행, 결과 생성, 공개 및 순위 조회 |

CI/CD 파이프라인의 생성과 변경 권한은 4조가 관리한다. 다른 조가 파이프라인 변경이 필요할 경우 변경 사유와 예상 영향을 Issue로 제출한다.

## 9. 4조 역할 분담

저장소의 현재 담당 체계를 기준으로 다음과 같이 역할을 매핑한다. 프로젝트 상황에 따라 겸임하거나 재조정할 수 있다.

| 역할 | 담당 | 주요 책임 |
|---|---|---|
| 형상관리 총괄 | P1 김여름 | 브랜치 정책, PR 규칙, CODEOWNERS 관리 |
| Core 모델 게이트키퍼 | P2 심우섭, P3 김종복 | `accounts`, `teams`, `rounds` 모델 및 Migration 검토 |
| CI/CD 담당 | P1 김여름, P6 황지나 | 파이프라인 구성, 배포 연계, 테스트 통과 여부 확인 |
| 1조 연동 창구 | P4 노희주 | `garden`과 Core 간 FK 및 기능 변경 조율 |
| 2조 연동 창구 | P5 전예진 | `lms`와 Core 간 FK 및 기능 변경 조율 |
| 3조 연동 창구 | P6 황지나 | `prd`와 Core 간 FK 및 기능 변경 조율, 문서 연계 |
| ERD 버전관리 | P3 김종복 | Migration과 통합 ERD의 일치 여부 확인 |

## 10. 표준 작업 절차

### 10.1 일반 기능 변경

1. 최신 `develop`을 기준으로 팀별 작업 브랜치를 생성한다.
2. 담당 앱 범위 안에서 기능을 개발하고 테스트한다.
3. Pull Request에 변경 목적, 테스트 결과, DB 영향 여부를 작성한다.
4. CODEOWNER 또는 팀 리뷰어의 승인을 받는다.
5. CI 통과 후 `develop`에 병합한다.

### 10.2 공유 테이블 변경

1. Core 스키마 변경 Issue를 작성한다.
2. 4조가 필요성과 전체 영향도를 검토한다.
3. 4조가 별도 `team4/기능명` 브랜치에서 모델·Migration·ERD를 수정한다.
4. Core 담당자 리뷰와 전체 테스트를 수행한다.
5. 승인 및 CI 통과 후 `develop`에 병합한다.

### 10.3 Phase 릴리스

1. 해당 Phase의 완료 조건을 확인한다.
2. `develop`에서 전체 통합 테스트를 수행한다.
3. 검증된 변경을 Pull Request로 `main`에 병합한다.
4. `main`의 해당 커밋에 `v0.x` 태그를 생성한다.
5. 릴리스 노트에 완료 범위와 알려진 문제를 기록한다.

- [ ] 변경 사항이 담당 앱 범위 안에 있는가?
- [ ] 공유 Core 모델을 직접 변경하지 않았는가?
- [ ] 공유 영역 변경 시 4조 승인 요청이 포함되었는가?
- [ ] 모델 변경에 대응하는 Migration이 포함되었는가?
- [ ] 스키마 변경 시 통합 ERD도 함께 갱신했는가?
- [ ] 관련 단위 테스트와 회귀 테스트를 수행했는가?
- [ ] Pull Request 설명에 영향 범위와 테스트 결과를 기록했는가?
- [ ] `develop` 또는 `main`에 직접 Push하지 않았는가?

## 12. 기대 효과

- 공유 테이블의 무분별한 변경과 Migration 충돌을 방지한다.
- 각 조의 개발 자율성과 Core 데이터의 안정성을 함께 확보한다.
- ERD와 실제 DB 구조가 달라지는 문제를 예방한다.
- 변경 책임과 리뷰 담당자가 명확해져 통합 과정의 의사소통 비용을 줄인다.
- 단계별 통합 테스트와 릴리스 태그를 통해 장애 발생 시 변경 이력을 쉽게 추적할 수 있다.

## 13. 최종 요약

본 형상관리 전략은 **모든 조가 하나의 저장소에서 협업하되, 공유 공간의 구조 변경은 4조가 통제하는 방식**이다. 각 조는 자기 앱을 자율적으로 개발하고, 공유 모델 변경은 요청·검토·Migration·ERD 갱신 절차를 거친다. 이를 Pull Request, CODEOWNERS, Branch Protection, CI 테스트로 강제하여 통합 플랫폼의 안정성을 유지한다.
