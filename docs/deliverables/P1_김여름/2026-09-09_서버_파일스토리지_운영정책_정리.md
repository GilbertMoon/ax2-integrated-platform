# 2026-09-09 서버·파일스토리지 운영정책 정리

담당: P1 김여름  
역할: 전체 통합 총괄 / 일정·Git·문서 기준 관리

## 1. 정리 목적

튜터/교수님 추가요청에 따라 4조가 공용 서버의 파일 저장 구조와 Web Client 업로드 권한 기준을 정하고, 1·2·3조가 동일한 기준을 사용하도록 안내하기 위한 운영정책 초안이다.

핵심 방향은 다음과 같다.

- 1·2·3조는 각 기능에서 실제로 발생하는 파일 요구사항과 현재 구현(AS-IS)을 전달한다.
- 공용 Root Folder, 하위 폴더, 파일명 규칙, Web Client 권한, DB 메타정보, 백업/복구 정책은 4조가 통합 기준으로 결정한다.
- 실제 파일은 File Storage에 저장하고, DB에는 파일 경로/크기/소유자/업로드 시각/관련 FK 등 메타정보를 저장하는 구조를 기본 방향으로 검토한다.
- 각 조가 운영 서버의 파일 경로나 DB 관리자 권한을 직접 임의 변경하지 않도록 한다.
- 각 조의 기존 구현은 호환성 판단 자료이며, 운영 서버 최종 기준은 4조가 주관하여 확정·안내한다.

## 2. 현재 서버 운영 현황

### SSH / 파일 전송
- Ubuntu 서버는 SSH 원격접속이 가능한 상태로 확인됨.
- PowerShell에서 SSH 접속 가능.
- `scp`를 이용한 DB Backup 파일의 서버 전송 방법 확인.
- 운영 보안 방식(SSH Key 등)은 실운영 전 별도 검토.

### DB 이관
현재 필요한 절차는 아래와 같다.

```text
기존 PostgreSQL DB Backup
        ↓
scp로 Ubuntu 서버 전송
        ↓
서버 PostgreSQL Restore
        ↓
Schema / FK / Table / Data 건수 검증
        ↓
Django 연결 및 Regression
```

공식 DB Host/Port/DB 기준은 팀 공통값으로 하나로 확정해야 한다.

## 4. 얼굴사진 저장정책 방향

얼굴사진은 용도가 다르므로 저장방식을 분리한다.

### 프로필 사진
- 현재 DB 저장 방식 유지 가능
- 사용자당 소수 파일이므로 현 단계에서는 기존 구현 유지 가능
- 향후 공용 File Storage로 통합할지 별도 검토

### 일별 출석 사진
- 누적량이 많으므로 File Storage 저장 방향
- DB에는 파일 자체가 아니라 경로와 메타정보 저장

예시:

```text
/srv/ax2/data/attendance/
└── users/
    └── user_28/
        ├── checkin_20260909_091532.jpg
        ├── checkin_20260910_090104.jpg
        └── checkin_20260911_085958.jpg
```

운영 화면에서는 사용자 이름을 표시하더라도 서버 폴더는 변하지 않는 `user_id` 기준으로 관리한다.

DB 예시:

```text
user_id = 28
attendance_id = ...
file_path = attendance/users/user_28/checkin_20260909_091532.jpg
captured_at = 2026-09-09 09:15:32
file_size = ...
```

## 5. 조별 파일 사용 현황

### 2조 PRD
현재 확인 결과:

- PRD는 DB 기반 Page/Document Data
- 사용자 파일 업로드 기능 없음
- MD Export 시 서버에 파일을 저장하지 않음
- 현재 PRD 자체는 공용 File Storage 직접 사용 대상이 아님
- 향후 이미지/첨부파일 기능 추가 시 4조 공통 정책 적용

추가 확인:
- 이미지 첨부 존재 여부
- Export 과정 임시파일 생성 여부
- 향후 첨부기능 계획 여부

### 3조 LMS — 현재 구현(AS-IS) 확인 완료

3조에서 전달받은 현재 구현은 다음과 같다.

#### 실제 저장 방식
- 파일 자체는 DB의 BYTEA/BLOB에 저장하지 않음.
- Storage Backend: `django.core.files.storage.FileSystemStorage`.
- 실제 파일은 서버 로컬 파일시스템에 저장.
- 기본 `MEDIA_ROOT`: `<BASE_DIR>/media`이며 환경변수 `MEDIA_ROOT`로 재정의 가능.
- 현재 개발 서버 기준 경로: `C:\Dev\assignment-lms\media`.
- S3/Object Storage는 사용하지 않음.

#### 저장 경로 규칙
과제 제출파일:

```text
<MEDIA_ROOT>/submissions/<제출자 user_id>/<uuid32>_<원본파일명>
```

과제 첨부자료:

```text
<MEDIA_ROOT>/assignment_files/<assignment_id>/<uuid32>_<원본파일명>
```

#### DB `submission_file` 저장 항목
- `id`: bigint PK
- `submission_id`: bigint FK → `submission.id`
- `kind`: `PY` / `IPYNB` / `OTHER`
- `file_url`: `/media/submissions/...` 형태의 상대 URL 문자열
- `file_name`: 원본 파일명
- `file_size`: byte 단위 크기
- 실제 파일 바이너리 및 파일시스템 절대경로는 DB에 저장하지 않음.
- GitHub 등 링크 제출은 디스크 파일을 만들지 않고 외부 URL만 `file_url`에 저장하며 `file_size=0`.

#### 현재 업로드/재제출 정책
- 파일 1개 최대 크기: 30MB.
- 최초 제출/재제출 공통 적용.
- 파일 개수 상한 없음.
- 확장자 White List / Black List / MIME 검사 없음.
- `.exe`, `.zip`, `.html` 등도 업로드 가능.
- `.py`, `.ipynb`만 미리보기 특별처리.
- `(assignment, 제출단위)`당 `Submission` 1행.
- 재제출 시 기존 `SubmissionFile` row 삭제 + `default_storage.delete`로 기존 디스크 파일 삭제 후 덮어쓰기.
- 제출 버전 이력 보관 없음.

#### 현재 삭제/보관 정책
- 학생의 제출 후 개별 삭제/철회 기능 없음.
- 학생은 재제출을 통한 덮어쓰기만 가능.
- 튜터의 과제 자체 Soft Delete는 가능하나 제출물은 남음.
- 제출물 개별 삭제 기능 없음.
- 보관기간 정책 없음: 코드상 무기한.
- 자동 삭제/만료/아카이브 Cron/Batch 없음.
- 개발 초기화용 `reset_domain_data`는 DB row만 제거하여 디스크에 고아 파일이 남을 수 있음.

#### 현재 업로드/다운로드 권한
- 학생은 본인 개인과제 또는 본인이 속한 팀 과제에 한해 접근.
- 본인 제출물 또는 소속팀 제출물만 접근 가능.

### 3조 AS-IS 확인 후 4조가 결정할 사항

위 내용은 3조의 현재 구현 현황이며 **통합 운영 정책 결정사항이 아니다.**
운영 서버에서는 4조가 주관하여 다음 항목을 결정하고 1·2·3조에 공통 기준으로 안내한다.

- `FileSystemStorage` 유지 여부
- 운영 서버의 실제 `MEDIA_ROOT` 위치
- `/media/` 제공 방식 및 `MEDIA_URL` 기준
- 기능별 공용 파일 저장 경로 규칙
- DB + File Storage의 동시 Backup/Restore 기준
- 서버 이관 시 파일 복사·검증 기준
- 업로드 허용 확장자 및 MIME 검사 정책
- 실행파일/HTML/압축파일 등 위험 파일 처리 기준
- 서비스 전체 저장공간 한도 및 모니터링 기준
- 무기한 보관 유지 여부 및 삭제/아카이브 정책
- 재제출 버전 보관 여부
- DB row 없는 고아 파일 정리 정책
- Web Client 업로드/다운로드 권한 기준

즉 3조는 현재 구현과 제약사항을 제공하고, **최종 서버·DB·File Storage 운영 기준은 4조가 결정한다.**

## 6. 3조 LMS GitHub URL 평가 방식의 운영 Pain Point

현재 학생이 GitHub Repository URL을 제출하고 평가자가 링크를 직접 열어 확인하는 방식은 File Storage 사용량은 줄일 수 있으나, 평가 운영 측면에서 다음 문제가 있다.

- 학생 수 × 과제 수만큼 평가자가 링크를 반복해서 열어야 함
- 단순 Repository URL만 저장하면 제출 시점의 상태가 고정되지 않음
- 제출 후 학생이 코드를 수정하면 평가 당시 상태와 현재 상태가 달라질 수 있음
- 어느 Branch/Commit을 평가했는지 추적하기 어려움
- 1차 제출/재제출/최종 제출 이력 관리가 약함
- 여러 평가자가 서로 다른 시점의 코드를 볼 수 있음
- Repository 삭제/Private 전환 시 과거 제출 결과 재확인이 어려움
- 평가 완료/미완료 상태가 사람의 기억이나 별도 기록에 의존할 수 있음
- 점수와 평가 근거의 Audit Trail이 약함

소스 전체를 서버에 저장하지 않더라도 LMS DB에는 최소한 아래 정보를 저장하는 구조가 필요하다.

```text
student_id
assignment_id
repository_url
branch
commit_sha
submitted_at
evaluated_at
evaluator_id
score
feedback
submission_status
```

필요 시 향후 제출 시점의 Snapshot ZIP/Git archive를 File Storage에 보관하는 방식도 검토할 수 있다.

## 7. Web Client 권한과 DB 권한 분리

교수님 요청사항은 4조가 Web Client 업로드 권한 및 공용 저장기준을 만들어 1·2·3조에 전달하는 방향으로 이해한다.

다음 권한은 서로 구분한다.

### 각 조에 제공 가능한 권한
- 웹에서 정해진 Upload 기능 사용
- 정해진 API/공통 업로드 모듈 사용
- 자기 기능 범위의 파일 조회/다운로드

### 제공하지 않아야 하는 권한
- PostgreSQL SuperUser 권한
- 운영 서버 Root 권한
- 공용 File Storage 전체 임의 삭제 권한
- 다른 조 파일에 대한 무제한 수정 권한

즉 `Web Client Upload 권한 != Server 관리자 권한 != DB 관리자 권한`으로 분리한다.
