# AX2 통합 플랫폼 형상관리 전략 — 쉬운 설명

## 1. 이 문서는 무엇을 설명하나요?

이 문서는 1·2·3·4조가 하나의 통합 플랫폼을 함께 개발할 때 지켜야 할 형상관리 규칙을 쉽게 설명한 자료이다.

형상관리는 어렵게 말하면 코드와 변경 이력을 관리하는 방법이고, 쉽게 말하면 다음을 정하는 일이다.

- 누가 어느 부분을 작업하는가?
- 작업한 코드를 어디에 올리는가?
- 누가 변경 내용을 확인하는가?
- 여러 사람의 작업을 언제 하나로 합치는가?
- 문제가 생기면 어떤 변경에서 발생했는지 어떻게 찾는가?

## 2. 한 문장으로 설명하면

> **하나의 공동 저장소를 사용하되, 모든 조가 함께 쓰는 핵심 데이터 구조의 열쇠는 4조가 관리하는 방식이다.**

집에 비유하면 각 조는 자기 방에서 자유롭게 작업할 수 있다. 하지만 모든 사람이 함께 쓰는 거실이나 현관의 구조를 바꾸려면 집 전체에 영향을 줄 수 있으므로 4조와 먼저 협의해야 한다.

## 3. 왜 하나의 저장소를 사용하나요?

모든 팀은 `ax2-integrated-platform`이라는 하나의 저장소에서 작업한다.

1·2·3조의 기능은 서로 달라도 다음과 같은 Core 데이터를 함께 사용한다.

- 사용자
- 학생
- 팀
- 평가 라운드
- 평가 결과

저장소를 조별로 나누면 한 조에서 사용자나 팀 구조를 변경했을 때 다른 조가 그 사실을 늦게 알 수 있다. 그러면 각 저장소의 DB 구조가 달라지고, 통합 시 Migration과 외래키 충돌이 발생하기 쉽다.

하나의 저장소를 사용하면 모든 조가 같은 Core 구조와 변경 이력을 보면서 개발할 수 있다.

## 4. 조별 작업 구역

| 담당 | 주로 작업하는 영역 | 설명 |
|---|---|---|
| 1조 | `garden/` | 게임형 프로그래밍 학습 기능 |
| 2조 | `lms/` | 강의, 과제, 제출, 피드백 기능 |
| 3조 | `prd/` | PRD, 아이디어 구체화, AI Coach 기능 |
| 4조 | `accounts/`, `teams/`, `rounds/`, `reviews/`, `results/`, `config/` 등 | 모든 조가 사용하는 Core 기능 |

`garden`, `lms`, `prd`는 통합 과정에서 기존 4조 프로젝트에 추가할 앱이다. 기존 4조 메인에는 사용자, 팀, 평가 라운드, 평가와 결과 앱이 이미 구성되어 있다.

## 5. 가장 중요한 규칙

1·2·3조는 자기 앱 안에서는 자율적으로 개발할 수 있다. 그러나 다음 공유 앱은 직접 수정하지 않고 4조에 변경을 요청한다.

- `accounts`: 공통 사용자
- `teams`: 공통 팀과 팀원 구성
- `rounds`: 평가 라운드와 참여자

`reviews`와 `results`도 평가 및 점수 계산의 중심이므로 변경할 때 반드시 4조의 리뷰를 받아야 한다.

### 예시: 1조에서 사용자 필드를 추가하고 싶은 경우

1조가 사용자에게 `고양이 닉네임`이 필요하다고 가정한다.

1. 1조가 `accounts/models.py`를 바로 수정하지 않는다.
2. GitHub Issue 또는 Core 스키마 변경 요청서를 작성한다.
3. 4조가 로그인, 학생 정보, 다른 조 기능에 미치는 영향을 확인한다.
4. 공통 필드가 맞다면 4조가 모델과 Migration을 변경한다.
5. DB 구조가 달라졌다면 같은 Pull Request에서 통합 ERD도 수정한다.
6. 관련 테스트가 통과하면 `develop`에 반영한다.

이 절차를 따르면 한 조의 필요로 추가한 변경 때문에 다른 조의 기능이 갑자기 동작하지 않는 문제를 줄일 수 있다.

## 6. 브랜치는 무엇인가요?

브랜치는 같은 저장소 안에서 작업 공간을 분리하는 기능이다. 원본 문서를 바로 고치지 않고 복사본에서 먼저 작업한 뒤, 검토가 끝나면 원본에 합치는 것과 비슷하다.

### 브랜치의 역할

| 브랜치 | 쉬운 설명 |
|---|---|
| `main` | 실제 배포할 수 있는 안정된 코드 |
| `develop` | 각 조의 작업을 모아서 함께 시험하는 코드 |
| `team1/기능명` | 1조의 개별 작업 공간 |
| `team2/기능명` | 2조의 개별 작업 공간 |
| `team3/기능명` | 3조의 개별 작업 공간 |
| `team4/기능명` | 4조의 개별 작업 공간 |

예를 들어 1조가 랭킹 기능을 개발한다면 `develop`을 기준으로 `team1/garden-ranking` 브랜치를 만든다.

```text
develop
 ├── team1/garden-ranking
 ├── team2/assignment-upload
 ├── team3/idea-voting
 └── team4/score-calculation
```

## 7. 평소에는 어떻게 작업하나요?

```text
1. develop에서 팀별 작업 브랜치 생성
                    ↓
2. 담당 기능 개발 및 테스트
                    ↓
3. develop을 대상으로 Pull Request 작성
                    ↓
4. 담당자 리뷰 및 CI 테스트
                    ↓
5. develop에 병합하여 통합 검증
                    ↓
6. 안정성이 확인되면 main에 병합
                    ↓
7. 실제 배포
```

- 자기 팀 앱만 변경했다면 같은 팀 리뷰어 1명의 승인 후 병합할 수 있다.
- 공유 Core 영역을 변경했다면 반드시 4조의 승인을 받아야 한다.
- 테스트가 실패한 코드는 병합하지 않는다.
- `develop`과 `main`에는 코드를 직접 Push하지 않고 Pull Request로 반영한다.

## 8. Pull Request는 무엇인가요?

Pull Request, 줄여서 PR은 “제가 이렇게 코드를 변경했으니 확인한 뒤 합쳐 주세요”라는 검토 요청이다.

PR에는 다음 내용을 적는다.

- 무엇을 변경했는가?
- 왜 변경했는가?
- 어떤 앱과 화면에 영향을 주는가?
- DB 구조가 바뀌는가?
- 어떤 테스트를 실행했는가?
- 리뷰어가 특별히 확인해야 할 부분은 무엇인가?

PR을 사용하면 코드를 합치기 전에 다른 사람이 실수나 영향 범위를 확인할 수 있고, 나중에 변경 이유도 추적할 수 있다.

## 9. CODEOWNERS는 무엇인가요?

CODEOWNERS는 파일이나 폴더별 담당자를 GitHub에 등록하는 설정이다.

```text
garden 변경     → 1조 또는 1조 연동 담당자 호출
lms 변경        → 2조 또는 2조 연동 담당자 호출
prd 변경        → 3조 또는 3조 연동 담당자 호출
Core 변경       → 4조 담당자 호출
CI/CD 변경      → 4조 형상관리 담당자 호출
```

예를 들어 누군가 `accounts/`를 변경한 PR을 올리면 GitHub가 4조 담당자를 자동으로 리뷰어로 요청한다.

CODEOWNERS 파일만 추가한다고 규칙이 완전히 강제되는 것은 아니다. GitHub의 `main`과 `develop` 보호 설정에서 다음 항목도 활성화해야 한다.

- PR 없이 직접 Push 금지
- CODEOWNER 승인 필수
- CI 테스트 통과 필수
- 승인 후 코드가 변경되면 재승인 필수

## 10. Migration은 무엇인가요?

Migration은 DB 구조의 변경 기록이다.

예를 들어 사용자 테이블에 전화번호 필드를 추가하면 코드만 수정해서는 실제 DB에 새 칸이 생기지 않는다. Django Migration이 어떤 테이블에 어떤 필드를 추가할지 기록하고 실제 DB에 적용한다.

Migration이 여러 조에서 동시에 잘못 만들어지면 적용 순서가 꼬이거나 같은 번호의 파일이 생길 수 있다. 그래서 소유권을 다음과 같이 나눈다.

- 1조는 `garden` 앱의 Migration을 관리한다.
- 2조는 `lms` 앱의 Migration을 관리한다.
- 3조는 `prd` 앱의 Migration을 관리한다.
- 4조는 `accounts`, `teams`, `rounds` 앱의 Migration을 관리한다.
- 공유 모델을 참조하는 외래키가 바뀌면 조별 연동 담당자와 먼저 협의한다.
- DB 구조가 바뀌면 Migration과 ERD를 같은 PR에서 수정한다.

핵심은 **실제 DB 구조와 설계 문서가 항상 함께 움직이게 하는 것**이다.

## 11. ERD는 왜 같이 수정하나요?

ERD는 테이블과 테이블 사이의 관계를 보여주는 DB 설계도이다.

Migration만 바꾸고 ERD를 수정하지 않으면 실제 건물과 설계도가 다른 것처럼 된다. 나중에 다른 팀원이 오래된 ERD를 보고 개발하면 잘못된 필드나 관계를 사용할 수 있다.

따라서 스키마 변경 PR에는 다음 두 가지가 함께 있어야 한다.

```text
Django 모델 및 Migration 변경
                +
통합 ERD Mermaid 원본 변경
```

## 12. CI/CD는 무엇을 하나요?

CI/CD는 코드가 올라왔을 때 테스트와 배포 준비를 자동으로 확인하는 장치이다.

### Pull Request 단계

PR에서는 변경된 영역을 중심으로 빠르게 검사한다.

- `garden/`만 변경되면 garden 관련 테스트를 실행한다.
- `lms/`만 변경되면 lms 관련 테스트를 실행한다.
- `prd/`만 변경되면 prd 관련 테스트를 실행한다.
- Core 앱이 변경되면 영향을 받는 여러 앱의 테스트를 실행한다.
- 공통 설정이 변경되면 전체 테스트를 실행한다.

### develop 및 main 단계

`develop`이나 `main`에 병합할 때는 전체 통합 테스트를 실행한다.

향후 서브팀 점수를 Core로 전송하는 기능이 추가되면 다음 흐름을 필수 회귀 테스트로 관리한다.

```text
서브팀에서 점수 전송
        ↓
ScoreInput 저장
        ↓
CalculationRun 실행
        ↓
EvaluationResult 생성
        ↓
최종 결과 조회
```

현재 기존 4조 메인에는 `CalculationRun`과 `EvaluationResult`는 있지만 `ScoreInput`은 아직 없다. `ScoreInput`의 구조와 전송 방식은 통합 설계 단계에서 4조가 확정한다.

## 13. Core가 바뀌면 무엇을 확인하나요?

Core 앱은 서로 연결되어 있으므로 한 앱을 바꾸면 연결된 기능도 함께 확인해야 한다.

| 변경 영역 | 함께 확인할 기능 |
|---|---|
| `accounts` | 로그인, 권한, 라운드 참여자, 팀, 평가, 결과 |
| `rounds` | 라운드 참여자, 팀, 평가, 결과 |
| `teams` | 팀원 구성, 평가, 결과 |
| `reviews` | 평가 제출, 잠금, 튜터 평가, 점수 계산 입력 |
| `results` | 계산 실행, 결과 생성, 공개, 순위 조회 |

## 14. 4조의 역할

4조는 모든 기능을 대신 개발하는 팀이 아니다. 각 조의 기능이 공통 Core와 안전하게 연결되도록 기준을 관리하는 팀이다.

| 역할 | 쉽게 말하면 |
|---|---|
| 형상관리 총괄 | 브랜치, PR, CODEOWNERS 규칙을 관리하는 사람 |
| Core 모델 게이트키퍼 | 공유 DB 구조 변경을 검토하는 사람 |
| CI/CD 담당 | 자동 테스트와 배포 흐름을 관리하는 사람 |
| 1조 연동 창구 | `garden`과 Core 사이의 변경을 조율하는 사람 |
| 2조 연동 창구 | `lms`와 Core 사이의 변경을 조율하는 사람 |
| 3조 연동 창구 | `prd`와 Core 사이의 변경을 조율하는 사람 |
| ERD 담당 | 실제 Migration과 ERD가 일치하는지 확인하는 사람 |

## 15. 상황별로 어떻게 하면 되나요?

| 상황 | 해야 할 일 |
|---|---|
| 자기 조 앱에 화면을 추가한다 | 팀별 브랜치에서 작업하고 팀 리뷰를 받는다. |
| 자기 조 앱에 테이블을 추가한다 | 자기 앱의 Migration과 ERD를 함께 수정한다. |
| 사용자 필드가 필요하다 | `accounts`를 직접 수정하지 않고 4조에 요청한다. |
| 팀 또는 라운드 구조를 바꾸고 싶다 | Issue를 작성하고 4조 Core 담당자와 협의한다. |
| 점수를 Core에 보내고 싶다 | `results` DB에 직접 저장하지 않고 정해진 Push 인터페이스를 사용한다. |
| 공통 설정이나 배포 파일을 바꾸고 싶다 | 4조 CI/CD 담당자에게 리뷰를 요청한다. |
| 스키마를 변경했다 | Migration과 통합 ERD를 같은 PR에 포함한다. |

## 16. 자주 묻는 질문

### Q1. 다른 조는 `accounts`, `teams`, `rounds`를 절대 수정할 수 없나요?

필요한 변경을 요청할 수는 있지만, 직접 수정해서 바로 병합하지는 않는다. 4조가 전체 영향을 확인하고 반영하거나, 협의 후 공동 작업한다.

### Q2. `develop`도 브랜치인가요?

그렇다. 각 조의 작업물을 먼저 모아 통합 시험을 하는 공동 브랜치이다. Git이 자동으로 만드는 브랜치가 아니므로 팀에서 생성하고 유지한다.

### Q3. 자기 조 앱만 바꿨는데도 4조 승인이 필요한가요?

자기 조 앱만 변경하고 공유 Core에 영향이 없다면 팀 내 리뷰 규칙을 적용할 수 있다. 다만 공유 모델 외래키, 인증, 점수 계산 또는 공통 설정에 영향을 준다면 4조 리뷰가 필요하다.

### Q4. 왜 `main`에 바로 올리면 안 되나요?

`main`은 배포 가능한 안정 상태를 유지해야 한다. 검증되지 않은 코드를 바로 올리면 전체 서비스에 장애가 발생할 수 있으므로 작업 브랜치와 `develop` 검증을 거친다.

### Q5. CODEOWNERS가 있으면 자동으로 병합되나요?

아니다. 담당 리뷰어를 자동으로 지정하는 기능이다. 실제 병합 조건은 Branch Protection Rules와 CI 설정으로 강제해야 한다.

## 17. 최종 요약

> **각 조는 자기 방에서는 자유롭게 작업하고, 모든 팀이 함께 쓰는 거실의 구조를 바꿀 때는 반드시 4조와 협의한다.**

이 규칙의 목적은 4조가 다른 조의 작업을 제한하는 것이 아니다. 각 조가 동시에 개발하더라도 공통 사용자·팀·평가 데이터가 깨지지 않게 하고, 문제가 생겼을 때 변경 원인과 책임 범위를 빠르게 찾기 위한 것이다.
