# TO-BE ERD 통합 설계서

> 기준일: 2026-09-02  
> 기준 ERD: `docs/erd/TO_BE_ERD_integrated_2026-09-01_Slack.mermaid`  
> 대상 저장소: `GilbertMoon/ax2-integrated-platform`  
> 작업 브랜치: `feature/p3-jb`

---

## 1. 문서 목적

본 문서는 2026-09-01 Slack 연동 내용을 포함한 최신 통합 TO-BE ERD를 기준으로, 통합 플랫폼의 핵심 데이터 모델과 조별 도메인 구조, 테이블 간 관계, 무결성 규칙 및 향후 DB 구현 시 확인해야 할 사항을 정리한다.

본 문서는 **ERD 구조 설명 문서**이며, 실제 운영 DB의 현재 스키마와 1:1로 동일하다는 의미는 아니다. 실제 DB 반영 여부는 별도의 DDL 및 스키마 검증 결과를 기준으로 판단한다.

---

## 2. 기준 ERD

최신 기준 ERD 파일:

- `docs/erd/TO_BE_ERD_integrated_2026-09-01_Slack.mermaid`
- 통합 TO-BE ERD v1
- 교수님 피드백 1~5 및 추가 확인사항 반영
- Slack 공통 연동 구조 반영

최신 ERD에서는 `accounts_user`를 공통 사용자 기준 엔터티로 두고, `rounds_evaluationround`를 프로젝트/평가 회차의 기준 엔터티로 사용한다. 팀은 회차에 종속되며, 채점 결과는 `results_calculationrun`과 `results_evaluationresult`를 중심으로 통합한다.

---

## 3. 전체 데이터 모델 개요

통합 ERD는 다음 6개 영역으로 구성한다.

| 영역 | 핵심 엔터티 | 목적 |
|---|---|---|
| Core | `accounts_user`, `rounds_evaluationround`, `rounds_roundparticipant`, `teams_team`, `teams_teammembership` | 사용자·회차·참여자·팀 공통 기반 |
| 통합 채점 | `results_calculationrun`, `results_evaluationresult`, `results_scoreinput` | 공식 평가 결과와 외부 점수 입력 통합 |
| 1조 게임/학습 | `CG_USERS`, `CONCEPTS`, `TASKS`, `TASK_ATTEMPTS`, `USER_PROFICIENCY`, `ATTENDANCES`, `ROOMS`, `ROOM_PARTICIPANTS`, `ITEMS`, `INVENTORIES`, `HOUSE`, `PLACED_OBJECTS` | 게임화 학습 및 학습 참여 |
| 2조 과제/제출/평가 | `ASSIGNMENT`, `SUBMISSION`, `SUBMISSION_FILE`, `AI_EVALUATION`, `EVALUATION` | 과제 제출 및 AI/튜터 평가 |
| 3조 PRD | `PRDs` | PRD 작성·회차·팀 관리 |
| 4조 근태/얼굴인식 + Slack | `FACE_PROFILE`, `FACE_IMAGE`, `ATTENDANCE_RECORD`, `FACE_RECOGNITION_LOG`, `notifications_slackidentity` | 실제 근태/얼굴인식 및 공통 Slack 연동 |

## 4. Core 공통 영역

### 4.1 `accounts_user`

통합 플랫폼의 공통 사용자 기준 테이블이다.

주요 컬럼:

- `id` PK
- `email` UK
- `password`
- `role`
- `approval_status`

다음 도메인의 기준 사용자 관계가 `accounts_user`에서 시작한다.

- 프로젝트/평가 참여
- 팀 구성
- 1조 게임/학습 프로필
- 2조 과제 생성 및 평가
- 3조 PRD 작성
- 4조 실제 근태
- 얼굴 프로필
- Slack 사용자 연동

### 4.2 `rounds_evaluationround`

프로젝트 및 평가 회차의 기준 엔터티이다.

주요 컬럼:

- `id` PK
- `created_by` FK → `accounts_user.id`
- `title`
- `status`
- `team_score_weight`
- `personal_score_weight`

현재 최신 ERD에는 프로젝트 기간을 별도 `team_start`, `team_end` 컬럼으로 표현하지 않는다. 프로젝트 기간을 별도 관리하는 `project_info` 구조를 사용하는 경우에는 해당 구조와 ERD를 함께 정합성 검토해야 한다.

### 4.3 `rounds_roundparticipant`

사용자의 특정 회차 참여 정보를 관리한다.

주요 컬럼:

- `id` PK
- `user_id` FK → `accounts_user.id`
- `round_id` FK → `rounds_evaluationround.id`
- `student_number_snapshot`
- `display_name_snapshot`

사용자의 회차별 참여 이력과 당시 표시명/학번 스냅샷을 보존하는 역할을 한다.

### 4.4 `teams_team`

프로젝트 회차에 종속된 팀을 관리한다.

주요 컬럼:

- `id` PK
- `round_id` FK → `rounds_evaluationround.id`
- `team_number`
- `name`

최신 ERD에서는 다음 관계를 명시한다.

`rounds_evaluationround 1 : N teams_team`

따라서 팀 조회 시 프로젝트/평가 회차 기준을 함께 고려한다.

### 4.5 `teams_teammembership`

회차 참여자와 팀의 소속 관계를 연결하는 테이블이다.

주요 컬럼:

- `id` PK
- `team_id` FK → `teams_team.id`
- `participant_id` FK → `rounds_roundparticipant.id`

관계:

`teams_team 1 : N teams_teammembership`  
`rounds_roundparticipant 0..1 : 0..1 teams_teammembership`

최신 ERD에서는 참여자 한 명의 팀 소속 관계를 선택적으로 표현한다.

## 5. 통합 채점 영역

### 5.1 `results_calculationrun`

특정 회차의 채점 실행 단위를 관리한다.

주요 컬럼:

- `id` PK
- `round_id` FK
- `status`
- `is_active`

관계:

`rounds_evaluationround 1 : N results_calculationrun`

### 5.2 `results_evaluationresult`

최종적으로 산출된 팀/개인 평가 결과를 관리한다.

주요 컬럼:

- `id` PK
- `calculation_run_id` FK
- `team_id` FK
- `participant_id` FK
- `result_type`
- `final_score_raw`

핵심 규칙:

- `result_type = TEAM`이면 `team_id` 필수, `participant_id`는 NULL
- `result_type = INDIVIDUAL`이면 `participant_id` 필수, `team_id`는 NULL

즉, 팀 결과와 개인 결과의 대상 식별자는 XOR 관계로 관리한다.

### 5.3 `results_scoreinput`

1~3조 등 외부 도메인에서 확정된 점수를 통합 채점 시스템으로 전달하기 위한 입력 테이블이다.

주요 컬럼:

- `id` PK
- `calculation_run_id` FK
- `participant_id` FK
- `team_id` FK
- `source_type`
- `source_id`
- `raw_score`
- `weight`
- `idempotency_key` UK
- `pushed_at`
- `created_at`

핵심 규칙:

- 개인 점수 입력: `participant_id`만 지정
- 팀 점수 입력: `team_id`만 지정
- `participant_id`와 `team_id`는 XOR
- `idempotency_key`는 중복 push 방지용 UK

2조 `SUBMISSION`과 `results_scoreinput` 사이에는 논리적 점수 push 관계가 존재한다. 최신 ERD에서는 이를 실선 FK가 아닌 점선 관계로 표현한다.

## 6. 1조 게임 / 학습 영역

1조 도메인은 공통 사용자와 연결되는 게임화 학습 영역이다.

### 6.1 사용자/학습

| 테이블 | 주요 역할 |
|---|---|
| `CG_USERS` | `accounts_user`의 1:1 게임/학습 프로필 확장 |
| `CONCEPTS` | 학습 개념 |
| `TASKS` | 학습 문제 |
| `TASK_ATTEMPTS` | 문제 풀이 기록 |
| `USER_PROFICIENCY` | 사용자별 개념 숙련도 |
| `ATTENDANCES` | 학습 참여/출석 |

`CG_USERS.id = accounts_user.id` 관계를 사용하며 계정 기본 정보를 중복 저장하지 않는다.

### 6.2 게임/방

| 테이블 | 주요 역할 |
|---|---|
| `ROOMS` | 게임/학습 방 |
| `ROOM_PARTICIPANTS` | 방 참가자 및 팀 배틀 |
| `teams_team` | 프로젝트 팀과 연계 |

`ROOM_PARTICIPANTS.team_id`를 통해 공통 프로젝트 팀과 연결할 수 있다.

### 6.3 아이템/하우스

| 테이블 | 주요 역할 |
|---|---|
| `ITEMS` | 게임 아이템 |
| `INVENTORIES` | 사용자 아이템 보유량 |
| `HOUSE` | 사용자 하우스 |
| `PLACED_OBJECTS` | 하우스 내 아이템 배치 |

관계:

- `ITEMS → INVENTORIES`
- `ITEMS → PLACED_OBJECTS`
- `CG_USERS → HOUSE`
- `HOUSE → PLACED_OBJECTS`
- `CG_USERS → ITEMS` 관계는 벽지/바닥 아이템 선택을 위한 논리 관계로 표현된다.

### 6.4 학습 출석과 실제 근태 분리

1조 `ATTENDANCES`와 4조 `ATTENDANCE_RECORD`는 목적이 다르므로 통합하지 않는다.

- `ATTENDANCES`: 게임/학습 참여 목적
- `ATTENDANCE_RECORD`: 실제 출퇴근/근태 목적

## 7. 2조 과제 / 제출 / 평가 영역

### 7.1 `ASSIGNMENT`

과제를 관리한다.

주요 컬럼:

- `id` PK
- `title`
- `description`
- `due_at`
- `is_required`
- `allow_late`
- `is_team`
- `created_by` FK
- `created_at`
- `updated_at`
- `deleted_at`

`accounts_user`가 과제를 생성한다.

### 7.2 `SUBMISSION`

과제 제출물을 관리한다.

주요 컬럼:

- `id` PK
- `assignment_id` FK
- `student_id` FK
- `team_id` FK
- `target_rule`
- `description`
- `submitted_at`
- `is_locked`
- `final_score`

핵심 규칙:

`student_id XOR team_id`

즉 개인 제출이면 `student_id`, 팀 제출이면 `team_id`를 지정한다.

`final_score`는 `EVALUATION.score`를 캐시한 값으로 정의되어 있으며, 공식 점수의 Source of Truth는 `EVALUATION.score`이다.

### 7.3 평가

- `SUBMISSION → AI_EVALUATION`: AI 1차 평가
- `SUBMISSION → EVALUATION`: 튜터 공식 평가

`EVALUATION.score`가 공식 평가 점수이며 `evaluated_by`를 통해 평가자를 연결한다.

### 7.4 첨부파일

`SUBMISSION_FILE`은 제출물의 파일 첨부 정보를 관리한다.

## 8. 3조 PRD 영역

`PRDs`는 제품 요구사항 문서 및 관련 산출물을 관리한다.

주요 컬럼:

- `prd_id` PK
- `template_id` FK
- `user_id` FK
- `round_id` FK → `rounds_evaluationround.id`
- `team_id` FK → `teams_team.id`
- `title`
- `status`
- `deadline`
- `is_deleted`
- `created_at`
- `updated_at`

핵심 관계:

- `accounts_user → PRDs`
- `rounds_evaluationround → PRDs`
- `teams_team → PRDs`

`template_id`는 최신 ERD 설명상 컬럼은 존재하지만, 실제 SQL에서 FK를 정의하지 않은 경우 별도 관계로 확정하지 않는다.

## 10. Slack 공통 연동 영역

최신 ERD에는 Slack 워크스페이스 사용자와 프로젝트 사용자 간 연동을 위한 `notifications_slackidentity`가 추가되어 있다.

### 10.1 `notifications_slackidentity`

주요 컬럼:

- `id` PK
- `user_id` FK → `accounts_user.id`, 미연동 상태에서는 NULL 허용
- `slack_user_id` UK
- `slack_email`
- `slack_display_name`
- `is_active`
- `synced_at`

관계:

`accounts_user 1 : 0..1 notifications_slackidentity`

### 10.2 Slack 연동 흐름

1. Slack `users.list`로 워크스페이스 멤버를 동기화한다.
2. `slack_email = accounts_user.email`이면 자동 연결한다.
3. 이메일이 없거나 일치하지 않으면 `user_id = NULL`인 미연동 Slack Identity로 저장한다.
4. 관리자가 프로젝트 User와 수동 연결한다.
5. 다른 팀은 공통 함수 `send_slack_dm_ax(ax_user_id, title, message, link)`를 호출한다.
6. `ax_user_id → accounts_user → notifications_slackidentity → slack_user_id` 순서로 대상 Slack 사용자를 찾는다.
7. `conversations.open → chat.postMessage` 방식으로 DM을 발송한다.

Slack 연동은 각 팀에서 별도의 Slack 사용자 매핑 로직을 구현하지 않고 공통 사용자 ID를 기준으로 처리하는 것을 원칙으로 한다.

## 12. 무결성 규칙

최신 ERD에서 명시한 핵심 무결성 규칙은 다음과 같다.

| 대상 | 규칙 |
|---|---|
| `results_evaluationresult` | `TEAM`이면 `team_id`만, `INDIVIDUAL`이면 `participant_id`만 사용 |
| `results_scoreinput` | `participant_id XOR team_id` |
| `SUBMISSION` | `student_id XOR team_id` |
| `teams_team.round_id` | `rounds_evaluationround.id` 참조 |
| `PRDs.round_id` | `rounds_evaluationround.id` 참조 |
| `CG_USERS.id` | `accounts_user.id`와 1:1 PK/FK |
| `notifications_slackidentity.slack_user_id` | Slack Member ID UK |
| `notifications_slackidentity.user_id` | 프로젝트 User 미연동 시 NULL 허용 |

가능한 경우 위 규칙은 애플리케이션 코드만이 아니라 PostgreSQL `CHECK`, `FK`, `UNIQUE` 등의 DB 제약조건으로 구현한다.

## 13. 프로젝트 기간(`project_info`) 관련 정합성 확인

현재 별도 VIEW 설계에서는 `project_info`가 `evaluationround_id`를 통해 `rounds_evaluationround`와 연결되고, `team_start`, `team_end`를 `project_info`에서 제공하는 구조를 사용하고 있다.

따라서 다음 두 산출물 간 정합성을 유지해야 한다.

- `docs/erd/TO_BE_ERD_integrated_2026-09-01_Slack.mermaid`
- `docs/erd/VIEW_GUIDE.md`

현재 최신 Mermaid ERD 본문에는 `project_info` 엔터티가 명시되어 있지 않으므로, **프로젝트 기간을 `project_info`에서 관리하는 설계를 최종 확정할 경우 다음 ERD 개정에서 `project_info`를 명시적으로 반영하는 것이 필요하다.**

이는 `rounds_evaluationround`에 `team_start`, `team_end`, `team_round`를 직접 추가하는 방식과 중복 관리하지 않기 위한 중요한 정합성 항목이다.

## 14. 기존 설계에서의 주요 변경 방향

### 14.1 프로젝트 기간 정보

기존 검토 과정에서 `rounds_evaluationround`에 다음 컬럼을 직접 추가하는 방안을 검토했다.

- `team_start`
- `team_end`
- `team_round`

그러나 현재 VIEW 설계에서는 프로젝트 기간을 `project_info`에서 관리하는 방향이 사용되고 있다.

따라서 최종 DB 설계에서는 **프로젝트 기간 정보의 단일 Source of Truth를 명확히 결정해야 한다.**

### 14.2 평가와 프로젝트 기간 분리

`evaluation_start_at`, `evaluation_end_at`는 평가 기간의 의미를 가지며, 프로젝트 수행 기간과 동일한 개념으로 취급하지 않는다.

프로젝트 기간이 별도 테이블로 관리된다면 다음과 같이 개념을 분리한다.

```text
프로젝트 회차
 ├─ 프로젝트 기간: project_info.team_start ~ team_end
 └─ 평가 기간: rounds_evaluationround.evaluation_start_at ~ evaluation_end_at
```

### 14.3 1조 출석과 4조 근태 분리

학습 참여를 위한 `ATTENDANCES`와 실제 출퇴근을 위한 `ATTENDANCE_RECORD`를 통합하지 않는다.

### 14.4 공식 평가 점수와 외부 점수 입력 분리

- 2조 공식 평가: `EVALUATION.score`
- 외부 도메인 점수 전달: `results_scoreinput`
- 통합 계산 결과: `results_evaluationresult`

각 단계의 Source of Truth를 구분한다.

## 16. VIEW와의 관계

현재 통합 플랫폼에서 사용자/팀/프로젝트 정보를 조회하는 주요 VIEW는 다음과 같다.

### `public.ax_user_team_login_view`

사용자 로그인 및 현재/최근 팀 정보를 조회하는 목적의 VIEW이다.

현재 VIEW 정의에서는 `project_info`를 LEFT JOIN하여 다음 정보를 제공한다.

- `project_info_id`
- `team_start`
- `team_end`

### `public.user_round_team_view`

사용자-회차-팀 정보를 조회하는 목적의 VIEW이다.

현재 VIEW 정의에서는 다음 프로젝트 정보를 함께 제공한다.

- `project_info_id`
- `team_start`
- `team_end`

상세 SQL과 검증 방법은 `docs/erd/VIEW_GUIDE.md`를 기준으로 한다.

## 17. 최종 설계 원칙

1. `accounts_user`를 통합 플랫폼의 공통 사용자 기준으로 사용한다.
2. 회차 참여자는 `rounds_roundparticipant`를 통해 관리한다.
3. 팀은 `teams_team`, 팀 소속은 `teams_teammembership`으로 분리한다.
4. 프로젝트 회차와 평가 기간의 의미를 혼합하지 않는다.
5. 프로젝트 기간의 Source of Truth는 최종 확정 후 단일 위치에서 관리한다.
6. 1조 학습 출석과 4조 실제 근태를 분리한다.
7. AI 평가와 튜터 공식 평가를 분리하고 공식 점수의 Source of Truth를 명확히 한다.
8. 외부 점수는 `results_scoreinput`을 통해 통합 채점으로 전달한다.
9. 팀/개인 대상 점수는 XOR 무결성 규칙으로 보호한다.
10. Slack 연동은 `accounts_user`를 중심으로 공통화한다.
11. DB의 핵심 무결성 규칙은 가능한 경우 PostgreSQL 제약조건으로 강제한다.
12. ERD, DDL, VIEW, Django 모델 사이의 구조적 정합성을 지속적으로 검증한다.
