# Daily Team Feedback

이 폴더는 **AX2 3차 프로젝트의 일일 진행상황과 튜터 피드백**을 날짜별로 관리합니다.

목적은 누가 잘했고 못했는지를 평가하는 것이 아니라, 매일 아침 각 담당자가 아래 3가지를 바로 알 수 있게 하는 것입니다.

1. **어제 무엇이 확인되었는가?**
2. **오늘 무엇을 어떤 순서로 해야 하는가?**
3. **어디까지 해야 DONE으로 볼 수 있는가?**

---

## 1. 파일 사용 방법

매일 날짜별 파일을 하나 생성합니다.

```text
docs/daily-feedback/
├── README.md
├── 2026-08-28.md
├── 2026-08-29.md
└── ...
```

### 아침에 팀원이 할 일

1. 오늘 날짜의 피드백 파일을 엽니다.
2. 상단의 **팀 전체 현황**을 먼저 확인합니다.
3. 자기 이름(P1~P6)을 찾습니다.
4. **어제 확인된 내용 → 피드백 → 오늘 작업 순서 → DONE 기준** 순서로 읽습니다.
5. 오늘 작업은 문서에 적힌 순서를 기준으로 진행합니다.
6. 작업이 끝나면 본인 GitHub Issue에 결과를 남깁니다.
7. 마지막으로 DONE 기준을 하나씩 다시 확인합니다.

> 체크박스는 "해본 것 같다"가 아니라 **결과를 확인할 수 있을 때만** 완료 처리합니다.

## 2. 상태 표시 기준

| 상태 | 의미 | 행동 |
|---|---|---|
| 🟢 정상 진행 | 예정한 핵심 업무가 진행되고 결과가 확인됨 | 다음 단계 진행 |
| 🟡 진행 중 | 일부 완료했지만 핵심 확인이 더 필요함 | 미완료 MUST 우선 처리 |
| 🔴 확인 필요 | GitHub에서 진행 결과 확인이 어렵거나 핵심 업무가 미완료 | 새 작업보다 현재 업무 정리 우선 |
| ⛔ BLOCKED | 본인이 해결하기 어려운 외부 의존성 때문에 진행 불가 | Issue에 막힌 이유와 필요한 도움 기록 |

상태는 사람에 대한 평가가 아니라 **현재 업무의 가시성과 완료 정도**를 표시합니다.

---

## 3. 모든 팀원이 지켜야 할 기본 진행 순서

### STEP 1. Issue를 먼저 확인합니다

본인에게 지정된 Issue의 목적과 DONE 기준을 먼저 읽습니다.

### STEP 2. 실제 상태를 확인합니다

문서나 ERD만 보고 구현 여부를 추측하지 않습니다.

가능한 경우 다음을 직접 확인합니다.

- Repository / Branch / Commit
- 프로젝트 실행 성공/실패
- 화면 접근 가능 여부
- Model / Table / FK 관계
- Migration 상태
- 테스트 결과

### STEP 3. 작업 결과를 남깁니다

작업 후 Issue에 최소한 아래 형식으로 기록합니다.

```md
## 오늘 완료한 작업
- [x] ...
- [x] ...

## 확인 결과
- 실행 결과:
- 확인한 화면/기능:
- 변경/결정 사항:

## 남은 작업
- [ ] ...

## 막힌 점 / 다른 담당자 확인 필요
- 없음
```

막힌 점이 없으면 반드시 `없음`이라고 적습니다.

### STEP 4. DONE 기준을 다시 검증합니다

다음 질문에 모두 답할 수 있어야 완료입니다.

- 무엇을 했는가?
- 실제로 정상인지 어떻게 확인했는가?
- 결과가 어디에 기록되어 있는가?
- 다른 사람이 같은 결과를 다시 확인할 수 있는가?

하나라도 설명하기 어렵다면 `DONE`이 아니라 `DOING` 또는 `REVIEW`입니다.

---

## 4. 증거가 있어야 완료로 인정하는 항목

| 작업 | 권장 확인 증거 |
|---|---|
| 프로젝트 실행 | 실행 명령 + 성공/실패 결과 |
| 기능 확인 | 화면/URL + 확인한 기능 |
| ERD 결정 | 변경된 관계/테이블과 판단 이유 |
| DB 작업 | DB명/버전/Migration/Backup 결과 |
| 코드 변경 | Branch/Commit/PR |
| 테스트 | 실행한 시나리오 + PASS/FAIL |
| 서버 점검 | OS/CPU/RAM/IP/Python/Git/PostgreSQL 등 실제 값 |
| 막힘 | 에러 메시지 + 재현 방법 + 필요한 도움 |

## 5. Issue 작성 원칙

### 좋은 기록

```text
2조 프로젝트 로컬 실행 성공
Branch: main
로그인 후 /assignments/ 접근 확인
학생 계정으로 과제 목록 조회 성공
```

### 부족한 기록

```text
확인했습니다.
거의 됐습니다.
진행 중입니다.
```

결과를 다른 팀원이 재현할 수 있을 정도로 짧고 구체적으로 작성합니다.

날짜별 문서는 다음 순서를 사용합니다.

## 7. 가장 중요한 운영 원칙

- **Core 기준은 기존 4조 시스템을 우선합니다.**
- User / Student / Team 같은 공통 데이터는 중복 생성하지 않습니다.
- 1조 → 2조 → 3조 순서로 통합합니다.
- 각 조 통합 후 기존 4조 기능 Regression을 확인합니다.
- 1조 학습 출석과 4조 실제 근태는 별도 Domain으로 유지합니다.
- DB 변경은 Migration으로 재현 가능해야 합니다.
- 실제 코드와 실행 상태를 확인하지 않은 항목은 완료 처리하지 않습니다.
- 작업 결과와 의사결정은 반드시 GitHub에 남깁니다.
